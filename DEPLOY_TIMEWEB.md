# Развёртывание ПожТендера в Timeweb Cloud

Проект запускается как backend-приложение из `Dockerfile`. Контейнер слушает порт `8080`, а проверку состояния Timeweb выполняет по адресу `/health`.

## Создание приложения

1. Поместить этот каталог в приватный Git-репозиторий. Секреты и файл `.env` не добавлять.
2. В Timeweb Cloud открыть **App Platform → Создать приложение → Backend → Dockerfile**.
3. Подключить репозиторий и ветку, содержащую сайт. Контекст сборки — корень репозитория, Dockerfile — `Dockerfile`.
4. Указать порт `8080` и healthcheck `/health`.
5. Сначала развернуть без боевых секретов. Timeweb выдаст технический домен с HTTPS.
6. В переменных приложения задать `PUBLIC_ORIGIN` равным выданному HTTPS-адресу без завершающего `/`.

## База данных

Заказы и выданные доступы хранятся в **Neon PostgreSQL** — это внешний
managed-сервис, а не база Timeweb. Приложение в Timeweb App Platform, база в Neon.

Добавлять только в панели Timeweb, не в Git:

- `DATABASE_URL` — обязательна. Без неё касса не открывается: платёж, который
  нельзя записать, не должен начинаться.
- `DATABASE_POOL_MAX` — необязательна, по умолчанию 5.

TLS задаётся исключительно параметрами `DATABASE_URL`. Отдельной переменной для
режима TLS нет и быть не должно: node-postgres накладывает разобранную строку
подключения поверх `ssl`-объекта из кода, поэтому вторая настройка молча
игнорировалась бы.

В строке подключения используйте `sslmode=verify-full`. Сертификат Neon выпущен
публично доверенным CA, поэтому проверка цепочки и имени хоста работает на
встроенном хранилище доверия Node — CA-бандл не нужен. Значение `require` не
используйте: pg 8 пока трактует его как `verify-full`, но сам предупреждает, что
в pg 9 этот режим перестанет проверять сертификат. Режимы `disable`, `allow` и
`no-verify` для удалённого хоста приложение отвергает при запуске.

Neon даёт две строки подключения:

- **pooled** (хост с суффиксом `-pooler`) — для `DATABASE_URL` приложения;
- **direct** (без `-pooler`) — для миграций.

Миграции применяются один раз, с direct-строкой в окружении:

```bash
export DATABASE_URL='postgresql://…direct-host…/DBNAME?sslmode=verify-full'
npm run db:migrate
```

## Оплата от ИП и организаций

Robokassa принимает платежи **только от физических лиц** (подтверждено
поддержкой). ИП и организации оплачивают банковским переводом: заказ создаётся
со статусом `awaiting_bank_payment`, Robokassa не задействуется.

- `BANK_TRANSFER_DETAILS` — необязательная переменная со свободным текстом
  реквизитов, который показывается на `/payment/invoice`. Если не задана,
  страница сообщает покупателю, что счёт будет выслан на email.

После поступления денег на счёт оплата подтверждается вручную:

```bash
export DATABASE_URL='postgresql://…?sslmode=verify-full'
node scripts/confirm-bank-payment.mjs <НОМЕР_ЗАКАЗА>
```

Затем чек НПД выставляется вручную в «Мой налог» на покупателя с указанием его
ИНН. Публичного endpoint для подтверждения оплаты нет намеренно.

## Переменные Robokassa

Добавлять только в панели Timeweb, не в Git:

- `ROBOKASSA_MERCHANT_LOGIN`
- `ROBOKASSA_PASSWORD_1`
- `ROBOKASSA_PASSWORD_2`
- `ROBOKASSA_TEST_MODE=true` для первой проверки
- `ROBOKASSA_B2B_RECEIPT_CONFIRMED=false` до готовности принимать боевые карточные платежи. Имя историческое: к B2B-чекам переменная отношения не имеет — организации через Robokassa не платят. Это второе явное подтверждение, без которого боевой режим не открывается. При `ROBOKASSA_TEST_MODE=true` тестовая оплата доступна и с этим безопасным значением.

Пока последняя переменная равна `false`, кнопка оплаты безопасно ведёт на страницу «Онлайн-оплата подключается» и не создаёт платёж.

## Настройки магазина Robokassa

После получения постоянного домена указать в кабинете магазина:

- Result URL: `https://ДОМЕН/api/payment/result`
- Success URL: `https://ДОМЕН/payment/success`
- Fail URL: `https://ДОМЕН/payment/failed`
- метод Result URL: POST (сайт также принимает GET)
- алгоритм подписей: SHA-256

Сначала провести тестовый платёж от физического лица. Включать боевой режим (`ROBOKASSA_TEST_MODE=false` **и** `ROBOKASSA_B2B_RECEIPT_CONFIRMED=true`) только после проверки, что чек НПД формируется и доходит до покупателя.
